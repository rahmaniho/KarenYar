# یکپارچگی کارو با بک‌اند Laravel

این سند توضیح می‌دهد نسخهٔ متصل‌به‌سرور (پوشهٔ `laravel-backend/`) چطور با اپ
اصلی (`src/`) هم‌گام می‌ماند، چه چیزی در حالت سروری فرق دارد و چه کارهایی
باقی مانده است.

## ۱) دو حالت اجرا از یک رابط کاربری

|            | اپ اصلی (PWA/اندروید)         | نسخهٔ لاراول                                   |
| ---------- | ----------------------------- | ---------------------------------------------- |
| منبع UI    | `src/`                        | `laravel-backend/resources/js/` (تولیدشده)     |
| داده       | Dexie/IndexedDB (آفلاین‌فرست) | دیتابیس لاراول از طریق `/api/sync/*`           |
| ورود       | لایسنس آفلاین (KS1/Ed25519)   | نشست لاراول + ایمیل/رمز                        |
| نقش‌ها     | همه‌ی امکانات محلی            | `manager` (پنل مدیر) و `store` (کاربر فروشگاه) |
| سرویس‌ورکر | دارد                          | ندارد (به‌شبکه نیاز دارد)                      |

هر دو از یک کد UI استفاده می‌کنند؛ تفاوت در «لایهٔ داده» و «احراز هویت» است.

## ۲) قاعدهٔ ساخت: `resources/js = src + overlay`

`laravel-backend/resources/js` **تولیدشده** است و مستقیم ویرایش نمی‌شود:

```bash
npm run sync:laravel-frontend     # بازسازی کپی
npm run check:laravel-frontend    # بررسی هم‌خوانی (در CI اجرا می‌شود)
```

اسکریپت `scripts/sync-laravel-frontend.mjs` این کارها را می‌کند:

1. کل `src/` را در `laravel-backend/resources/js/` کپی می‌کند (پاک‌سازی قبلی).
2. فایل‌های `laravel-backend/frontend-overlay/` را روی آن می‌نویسد.

`frontend-overlay/` تنها فایل‌هایی را دارد که در حالت سروری تفاوت دارند
(۵۲ فایل): لایهٔ داده، کلاینت API، ورود/مدیر، تست‌ها و فایل‌هایی که ایمپورت
`useLiveQuery` را از Dexie به لایهٔ سروری تغییر می‌دهند.

### جریان کار روزمره

- تغییر UI مشترک → در `src/` انجام می‌شود، بعد `npm run sync:laravel-frontend`.
- تغییر مخصوص لاراول → در `laravel-backend/frontend-overlay/<مسیر>` انجام
  می‌شود، بعد `npm run sync:laravel-frontend`.
- اگر CI شکست خورد، یعنی کپی با `src + overlay` هم‌خوان نیست؛ همان دو دستور
  بالا رفعش می‌کند.

## ۳) چه چیزی در نسخهٔ لاراول اضافه شده

| فایل                              | نقش                                                     |
| --------------------------------- | ------------------------------------------------------- |
| `core/api/client.ts`              | `apiFetch` با کوکی نشست + توکن CSRF (`XSRF-TOKEN`)      |
| `core/db/server-db.ts`            | جایگزین Dexie: pull یکجا در حافظه، push دسته‌ای و اتمیک |
| `core/db/use-live-query.ts`       | `useLiveQuery` با پشتیبانی از لایهٔ سروری               |
| `store/auth-store.ts`             | وضعیت ورود/نقش/فروشگاه/لایسنس                           |
| `features/auth/LoginPage.tsx`     | صفحهٔ ورود                                              |
| `features/manager/ManagerApp.tsx` | پنل مدیر کل: CRUD فروشگاه + صدور/تمدید لایسنس           |
| `app/App.tsx`                     | مسیر: Splash → Login → پنل مدیر یا پوستهٔ فروشگاه       |
| `app/Support/AuditLogger.php`     | ثبت رویداد در `audit_logs` (هرگز عملیات را نمی‌شکند)    |
| `features/manager/AuditPanel.tsx` | پنل «رویدادهای اخیر» با تاریخ جلالی و برچسب فارسی       |

در `core/db/db.ts` انتخاب لایه‌ی داده انجام می‌شود: در تست‌ها Dexie (با
`fake-indexeddb`) و در اجرای واقعی `ServerDB`.

### ۳.۱) دفتر رویدادها (Audit)

هر عملیات حساس در `audit_logs` ثبت می‌شود: ورود، خروج، ورود ناموفق/مسدود،
ساخت/ویرایش/حذف فروشگاه، تغییر لایسنس، انتقال داده و پاک‌سازی.

| مسیر                                           | دسترسی        | توضیح                      |
| ---------------------------------------------- | ------------- | -------------------------- |
| `GET /api/manager/audit?limit&store_id&action` | مدیر          | همهٔ رویدادها، با فیلتر    |
| `GET /api/audit?limit`                         | کاربر فروشگاه | فقط رویدادهای فروشگاه خودش |

پاسخ: `{ events: [{ id, action, storeId, storeName, userName, userEmail, subjectType, subjectKey, meta, ip, createdAt }] }`

قواعد طراحی:

- **فقط افزودن**: هیچ مسیری برای ویرایش یا حذف رویداد وجود ندارد.
- **بی‌صدا در برابر خطا**: `AuditLogger::record()` هر استثنایی را می‌بلعد؛ اگر
  ثبت لاگ شکست بخورد، خود عملیات (مثلاً ساخت فروشگاه) انجام می‌شود.
- **دامنهٔ داده**: کاربر فروشگاه هرگز رویداد فروشگاه دیگر را نمی‌بیند
  (تست‌شده در `tests/Feature/AuditTest.php`).

## ۴) مدل لایسنس در حالت سروری

لایسنس برای هر فروشگاه در سرور تعریف می‌شود (`licenses` + `PUT
/api/manager/stores/{id}/license`) و همراه `GET /api/me` برمی‌گردد. قرارداد
امنیتی حفظ شده است: **انقضا یا لغو لایسنس هرگز دسترسی به داده‌های خود کاربر و
خروجی گرفتن از آن‌ها را نمی‌بندد** — فقط امکانات نسخهٔ پولی (PDF/پشتیبان‌گیری
حرفه‌ای) محدود می‌شود.

## ۵) برند و دارایی‌ها

- `resources/views/app.blade.php`، `public/manifest.webmanifest` و
  `laravel-backend/package.json` با برند «کارو» به‌روزرسانی شده‌اند.
- تصاویر از `public/images/karo/*` خوانده می‌شوند؛ نسخهٔ قدیمی
  `images/hesabyar/*` حذف شد.
- فونت‌ها فقط وزیرمتن (`vazirmatn-*.woff2` + مجوز) هستند؛ فونت‌های
  IRANSans/Peyda که از پروژهٔ دیگری کپی شده بودند حذف شدند.

## ۶) همگام‌سازی افزایشی و هم‌زمانی

هر ردیف در سرور ستون `rev` دارد (شمارندهٔ یکنواختِ هر فروشگاه در جدول
`sync_counters`) و حذف‌ها به‌صورت نرم (`deleted_at`) انجام می‌شوند:

| مرحله                          | رفتار                                                                                                    |
| ------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `GET /api/sync/pull?since=REV` | فقط ردیف‌های تازه‌تر از آن rev؛ حذف‌شده‌ها با `__deleted: true`                                          |
| `POST /api/sync/push`          | هر op `baseRev` می‌فرستد؛ اگر ردیف سرور جلوتر رفته باشد، عملیات اعمال نمی‌شود و در `conflicts` برمی‌گردد |
| تعارض                          | سرور برنده است؛ کلاینت نسخهٔ سرور را جایگزین می‌کند و `conflictCount` را بالا می‌برد                     |
| `POST /api/sync/wipe`          | سنگ‌قبر برای همهٔ ردیف‌ها تا دستگاه‌های دیگر هم خالی شوند                                                |

آخرین `rev` در `localStorage` (کلید `karo-sync-rev`) نگه داشته می‌شود؛ اگر
فروشگاه/کاربر عوض شود (`storeId` پاسخ با کش نخواند) یک pull کامل انجام می‌شود.

## ۷) مهاجرت دادهٔ کاربران فعلی

کاربرِ اپ آفلاین از «تنظیمات ← پشتیبان‌گیری» فایل JSON می‌گیرد و در نسخهٔ
سروری «تنظیمات ← انتقال دادهٔ دستگاه به سرور» بارگذاری می‌کند:

- مسیر: `POST /api/sync/import` با همان ساختار فایل پشتیبان (`tables`).
- ادغامی و تکرارپذیر است: ردیف‌های موجود روی سرور دست‌نخورده می‌مانند.
- شناسه‌ها حفظ می‌شوند و درج به ترتیب والد→فرزند انجام می‌شود تا کلیدهای
  خارجی (مثلاً اقلام فاکتور) درست بمانند.
- سقف ۲۰۰٬۰۰۰ ردیف در هر فایل.

## ۸) استقرار روی `karo.karen-soft.ir`

بستهٔ آماده با این دستور ساخته می‌شود:

```bash
npm run build:laravel-package     # → deploy/laravel-app/artifacts/karo-laravel.zip
```

بسته شامل `public/build` است و `vendor/`/`node_modules/` را ندارد؛ نصب گام‌به‌گام
در [`deploy/laravel-app/INSTALL.md`](../deploy/laravel-app/INSTALL.md) آمده است.
خلاصه: Document Root زیردامنه → `.../laravel-backend/public`، نسخهٔ PHP 8.3+،
MySQL، `composer install --no-dev`، `php artisan migrate --force` و ساخت حساب
مدیر با tinker. **هیچ تغییری در DNS لازم نیست** چون دامنه از قبل روی همین cPanel
است؛ فقط اگر بخواهید به GitHub Pages برگردید، Document Root را دوباره به پوشهٔ
بستهٔ استاتیک تغییر دهید.

## ۹) محدودیت‌های باقی‌مانده

1. **بدون آفلاین**: در نسخهٔ لاراول همه‌ی خواندن/نوشتن از سرور است و
   سرویس‌ورکر ندارد. (اپ اصلی همچنان آفلاین است.)
2. **هم‌زمانی در سطح ردیف است، نه فیلد**: اگر دو دستگاه فیلدهای مختلف یک ردیف را
   عوض کنند، تغییرِ دومی به‌عنوان تعارض کنار گذاشته می‌شود (سرور برنده) — یعنی
   داده گم نمی‌شود ولی ممکن است کاربر باید ویرایش را تکرار کند.
3. **بدون تست بار (load test)**: رفتار pull/push با هزاران ردیف سنجیده نشده است.
4. **تاریخچهٔ شاخه**: کامیت `applied from amin gold` یک پروژهٔ دیگر را کامل
   کپی کرده بود و در کامیت بعد حذف شده است؛ درخت فعلی پاک است ولی تاریخچه
   شلوغ است.

## ۱۰) گام‌های بعدی پیشنهادی

- صفحهٔ «تعارض‌ها» برای مرور ردیف‌هایی که سرور برنده شده و امکان بازگرداندن
  ویرایش کاربر.
- pull صفحه‌بندی‌شده برای فروشگاه‌های خیلی بزرگ (هم‌اکنون هر pull افزایشی همهٔ
  تغییراتِ بعد از rev را یک‌جا می‌آورد).
