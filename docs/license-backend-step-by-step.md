# اجرای مرحله‌ای بک‌اند لایسنس و مدیریت حساب‌یار

## محدودهٔ تأییدشده

- فعال‌سازی برنامه و تمدید توکن لایسنس
- لغو و فعال‌سازی مجدد دستگاه توسط مدیر
- سقف دستگاه، پنل ادمین، صدور لایسنس و گزارش رویدادها
- دادهٔ مالی فقط روی دستگاه کاربر
- فایل بکاپ فقط روی گوشی/کامپیوتر خود کاربر ذخیره می‌شود — تأیید صریح کاربر

مرحلهٔ بعد: حساب کاربری فقط برای هویت، مجوز و دستگاه‌ها. آپلود بکاپ مالی، بکاپ ابری، سرور محلی جداگانه برای بکاپ و sync در محدودهٔ فعلی ساخته نمی‌شود.

> کیفیت با تست و معیار پذیرش سنجیده می‌شود. ادعای «۱۰۰٪ بدون باگ» تضمین فنی نیست.

## روش اجرا روی هاست

- هر پیام فقط یک اقدام مشخص روی staging و سپس انتظار برای تأیید کاربر.
- برای هر تغییر فایل روی هاست، **محتوای کامل فایل نهایی** به‌صورت یکپارچه تحویل می‌شود؛ ویرایش تکه‌ای و جست‌وجوی کد روی گوشی لازم نیست.
- agent به cPanel دسترسی ندارد؛ اعمال روی هاست فقط با تأیید کاربر ثبت می‌شود.
- فایل‌های خصوصی، کلید خصوصی و مشخصات دیتابیس داخل webroot، بستهٔ وب یا چت قرار نمی‌گیرند.
- production تا پایان پذیرش staging تغییر نمی‌کند.

## گام ۱ — اصلاح قرارداد کلید و امضا: بسته شد

### نتیجه

- decoder مشترک در `v1/license-encoding.php`، متصل به `activations.php` و `refresh.php`.
- ۲۰ تست encoding در PHP واقعی و تست sodium/Ed25519 در CI موفق.
- تست محافظت‌شدهٔ هاست در ۲۰۲۶-۱۱-۰۱: **۱۳/۱۳ PASS** سمت سرور و **OVERALL PASS** برای POST زنده.
- فایل موقت `admin/license-encoding-test.php` از مخزن و هاست حذف شد؛ حذف هاست را کاربر تأیید کرد.
- وب‌اپ staging در `/app/` نصب شد؛ مسیر صحیح لایسنس `/app/settings#license` است.
- صدور لایسنس واقعی staging، فعال‌سازی با نمایش «حرفه‌ای / فعال» و «بررسی آنلاین و تمدید» را کاربر در ۲۰۲۶-۱۱-۰۱ موفق اعلام کرد.
- کاربر حذف نصب‌کنندهٔ اولیهٔ `admin/deploy-app.php` از هاست را تأیید کرد.
- production دست‌نخورده است.

### اصلاح فنی

مرورگر کلید دستگاه و امضای refresh را با base64url بدون padding می‌فرستد. decoder مشترک اکنون:

- کلید عمومی دقیقاً ۳۲ بایت و امضا دقیقاً ۶۴ بایت را می‌پذیرد.
- base64url و base64 استاندارد قدیمی، با padding مجاز یا بدون آن، سازگارند.
- فاصله، خط جدید، padding خراب، طول اشتباه و بیت‌های انتهایی غیرکانونیکال را رد می‌کند.
- هیچ secret، دسترسی دیتابیس یا ارتباط شبکه‌ای ندارد.

فایل‌های مربوط:

```text
deploy/cpanel-staging/v1/license-encoding.php
deploy/cpanel-staging/v1/activations.php
deploy/cpanel-staging/v1/refresh.php
scripts/test-license-backend.mjs
.github/workflows/quality.yml
```

تست‌ها:

```text
npm run test:license-encoding
npm run test:license-backend
```

تست کامل نیاز به PHP 8.2+ و sodium دارد؛ CI آن را با PHP 8.3 اجرا می‌کند. صرف پاسخ `method_not_allowed` به GET، معیار قبولی POST نیست؛ آزمون واقعی مرورگر نیز انجام و تأیید شد.

سوابق CI اولیه: https://github.com/rahmaniho/KarenYar/actions/runs/41279043096

نسخهٔ بازگشت دو endpoint پیش از گام ۱ در پوشهٔ خصوصی زیر نگه‌داری می‌شود:

```text
/home/karensof/private/karen-staging/backups/pre-license-encoding-20261101/
```

نکتهٔ کش: برای بررسی `/app/` از query جدید استفاده کنید؛ پاسخ ۴۰۴ قدیمی ممکن است کش شده باشد. داده‌های سایت/IndexedDB را برای حل مشکل کش پاک نکنید.

## گام ۲ — اعتماد صریح کلاینت به issuer: بسته شد

### وضعیت

- کلید عمومی و `kid` را کاربر از فایل خصوصی متادیتا با cPanel خواند و ارائه کرد؛ هیچ کلید خصوصی دریافت نشد.
- اصلاح کلاینت، تست‌ها و بستهٔ staging در مخزن آماده‌اند.
- **انتشار بیلد پین‌شده در staging تأیید شد**: در ۲۰۲۶-۱۱-۰۱ صفحهٔ عمومی تنظیمات، `staging-ed25519-c6764aea4f3fda42` را زیر «کلید مورد اعتماد سرور» نمایش داد؛ asset جدید `index-BmUh7tMd.js` موجود بود و سرویس‌ورکر به آن و chunk جدید تنظیمات اشاره می‌کرد.
- کاربر در ۲۰۲۶-۱۱-۰۱ تأیید کرد: «کلید درست است و تمدید موفق بود»؛ آزمون پین و تمدید روی همان مرورگر قبلاً فعال‌شده موفق بود. نشست عمومی agent به داده‌های محلی دستگاه کاربر دسترسی ندارد.
- کاربر در ۲۰۲۶-۱۱-۰۱ انجام کپی بازگشت `app` در مسیر خصوصی تعیین‌شده را تأیید کرد.
- کاربر ساخت فایل کامل `admin/deploy-app.php` و فشردن دکمهٔ نصب را تأیید کرد؛ پیام موفقیت ندید. نتیجهٔ انتشار از وب‌اپ عمومی تأیید شد، اما علت نمایش‌ندادن پیام POST ادمین بدون دسترسی به نشست/لاگ هاست مشخص نیست. installer از بیرون همچنان 401 دارد؛ این حفاظت ادمین است، نه شاهد شکست نصب.
- پس از آزمون موفق، کاربر حذف نصب‌کنندهٔ جدید `admin/deploy-app.php` از هاست را در ۲۰۲۶-۱۱-۰۱ تأیید کرد. پاک‌سازی نصب‌کنندهٔ گام ۲ تکمیل شد؛ فایل منبع در مخزن برای بازبینی و تست باقی می‌ماند، نه داخل بستهٔ وب.

### اصلاح کلاینت

- در حالت سروری، `environment`، `issuer`، `audience`، `issuerKeyId` و کلید عمومی همگی اجباری‌اند.
- Vite هر build سروری فاقد این اطلاعات را پیش از تولید بسته متوقف می‌کند؛ نبود API همچنان حالت آفلاین/دمو را حفظ می‌کند.
- هم پاسخ activation/refresh و هم نشست ذخیره‌شده در IndexedDB از یک بررسی اعتماد مشترک استفاده می‌کنند.
- کلید پاسخ/نشست باید با کلید پین‌شده برابر باشد؛ base64 و base64url معادل، پس از canonicalization پذیرفته می‌شوند.
- امضا **فقط با کلید و `kid` موجود در build** بررسی می‌شود، نه با اطلاعات اعتماد معرفی‌شده توسط API یا IndexedDB.
- `iss` و `aud` دقیقاً بررسی می‌شوند؛ بررسی `env` در هدر و claims، الگوریتم، نوع، `kid`، محصول، دستگاه و زمان اعتبار نیز برقرار است.
- خطای انقضای توکن کد پایدار دارد و دیگر از متن ترجمه‌شده تشخیص داده نمی‌شود.
- نشست قبلی با کلید واقعی و قالب base64url، بدون ساخت دستگاه جدید قابل خواندن است.
- خطای اعتماد یا انقضا، اطلاعات مالی را پاک نمی‌کند و حق خروجی/بکاپ دستگاهی که قبلاً فعال شده حفظ می‌شود.
- صفحهٔ تنظیمات در بیلد جدید، «کلید مورد اعتماد سرور» و `kid` پین‌شده را نشان می‌دهد تا نسخهٔ کش‌شدهٔ قدیمی قابل تشخیص باشد.
- مسیرهای `/api`، `/v1` و `/admin` از fallback ناوبری سرویس‌ورکر خارج‌اند؛ درخواست‌های لایسنس همچنان POST و `no-store` و بدون کوکی‌اند.
- اسکریپت staging، `.htaccess` مخصوص `/app/` را قرار می‌دهد و فایل‌های مسیریابی ریشه/production را از خروجی staging حذف می‌کند.

### نصب‌کنندهٔ گام ۲

فایل کامل `deploy/cpanel-staging/admin/deploy-app.php` جایگزین نسخهٔ اولیهٔ نصب‌کننده شده است. این فایل به commit و SHA همین بسته اشاره می‌کند، نه بستهٔ قدیمی بدون pin.

- فقط روی webroot و محیط staging و با `REMOTE_USER`/`REDIRECT_REMOTE_USER` معتبر اجرا می‌شود؛ `PHP_AUTH_USER` به‌تنهایی اثبات احراز هویت نیست.
- GET فقط پیش‌بررسی و نمایش فرم است؛ دانلود و نصب فقط با POST، CSRF، rate limit و قفل استقرار انجام می‌شود.
- پیش از نصب، issuer/audience، `kid` و کلید عمومی متادیتای سرور و کپی بازگشت خصوصی بررسی می‌شوند. هیچ کلید خصوصی خوانده/منتشر نمی‌شود.
- فایل‌های راه‌انداز نسخهٔ فعلی و کپی بازگشت باید هم‌هش باشند؛ کپی ناقص یا قدیمی، نصب را متوقف می‌کند.
- دانلود HTTPS با بررسی اندازه و SHA-256؛ رد مسیر غیرمجاز، symlink، فایل اجرایی و آرشیو بزرگ.
- استخراج ابتدا در پوشهٔ خصوصی موقت انجام می‌شود؛ سپس assetها منتشر می‌شوند و فایل‌های راه‌انداز با rename فایل موقت جایگزین می‌شوند. assetهای هش‌دار قدیمی برای تب‌های باز حفظ می‌شوند.
- در خطای قابل‌گرفتن هنگام انتشار فایل‌های راه‌انداز، بازیابی هر چهار فایل از کپی خصوصی تلاش می‌شود. `deploy_failed_restored` یعنی این بازیابی موفق بوده؛ `rollback_required` یعنی باید متوقف شد و بازیابی دستی جداگانه بررسی شود.
- فایل‌های مالی/IndexedDB یا هویت دستگاه تغییر نمی‌کنند؛ به فایل‌های دیگر admin، v1 یا production دست زده نمی‌شود.
- تست PHP با ZIP واقعی، fixture خصوصی و تزریق خطا، در `scripts/test-staging-app-deploy.php` است؛ شبکه، bootstrap هاست، دیتابیس یا کلید خصوصی واقعی در تست بارگذاری نمی‌شود.
- آزمون نصب‌کننده و بازگشت در PHP 8.3 با zip و تمام quality gates در commit `dc7d4ee` موفق شدند: https://github.com/rahmaniho/KarenYar/actions/runs/41298320357 . انتشار عمومی و تمدید روی دستگاه اصلی تأیید شدند و کاربر حذف فایل نصب‌کننده از هاست را اعلام کرد.

```text

```

معیارهای گام ۲ تکمیل شدند (مشاهدهٔ عمومی agent و تأیید کاربر در مرورگر اصلی):

1. صفحهٔ لایسنس، `kid` مورد اعتماد بالا را نمایش می‌دهد؛ نشانگر بیلد جدید دیده و تأیید شد.
2. همان مرورگر قبلاً فعال‌شده برای آزمون استفاده شد؛ کد جدیدی برای گام ۲ درخواست/صادر نشد.
3. «بررسی آنلاین و تمدید» با کلید پین‌شده موفق شد؛ تأیید کاربر ثبت شد.
4. حذف فایل نصب‌کننده پس از پذیرش از webroot را کاربر تأیید کرد.

چرخش کلید، تغییر جداگانه و بازبینی‌شدهٔ build می‌خواهد؛ کلاینت نباید کلید جدیدی را خودکار از پاسخ API مورد اعتماد قرار دهد. production کلید و `kid` مستقل خودش را لازم دارد.

## گام ۳ — پایداری سرور: پاک‌ساز و آزمون عادی freshness بخش اول پذیرفته شدند؛ هماهنگی clock در مخزن آماده می‌شود

### یافتهٔ کد و اصلاح محدود ۳A

- activation ابتدا لایسنس را با `FOR UPDATE` می‌خواند و سپس دستگاه را؛ پنل فعلی admin نیز license سپس device را قفل می‌کند.
- نسخهٔ قبلی refresh یک SELECT دارای join از `license_devices` به `licenses` با `FOR UPDATE` دارد. ترتیب واقعی قفل‌های join به optimizer وابسته است و ترتیب صریح و مشترک با مسیرهای دیگر را تضمین نمی‌کند.
- اصلاح ۳A در `v1/refresh.php`: locator دستگاه برای یافتن `license_id` **بیرون تراکنش** خوانده می‌شود؛ سپس داخل تراکنش، ابتدا ردیف license با کلید اصلی و بعد ردیف device به‌صورت جداگانه قفل می‌شوند. تعلق دستگاه به همان license و وضعیت آن پس از قفل دوباره بررسی می‌شود. هیچ snapshot قدیمی با locator داخل تراکنش ایجاد نمی‌شود.
- وضعیت/کد محصول و وضعیت/مرجع مشتری با locking read و زیر قفل license خوانده می‌شوند؛ قفل‌های مشترک محصول/مشتری مانند مسیر activation، پیش از قفل device باقی می‌مانند. این بخش عمداً به یک خواندن snapshot بدون قفل تبدیل نشده است.
- قرارداد base64url، امضای دستگاه، شکل پاسخ، claims، انقضا، rate limit، خطاها و پاک‌سازی فعلی nonce تغییر نمی‌کنند. تغییر یا مهاجرت دیتابیس و فایل کمکی جدید روی هاست لازم نیست؛ فقط `refresh.php` جایگزین خواهد شد.
