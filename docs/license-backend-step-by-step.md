# اجرای مرحله‌ای بک‌اند لایسنس و مدیریت حساب‌یار

## محدودهٔ تأییدشده

- فعال‌سازی برنامه
- تمدید لایسنس
- لغو و فعال‌سازی مجدد دستگاه توسط مدیر
- سقف دستگاه
- پنل ادمین
- صدور لایسنس
- گزارش رویدادها
- دادهٔ مالی فقط روی دستگاه کاربر
- فایل بکاپ فقط روی گوشی/کامپیوتر خود کاربر ذخیره می‌شود — تأیید صریح کاربر

مرحلهٔ بعد: حساب کاربری برای هویت و مجوز. آپلود بکاپ مالی، بکاپ ابری، سرور محلی جداگانه برای بکاپ و sync در محدودهٔ فعلی ساخته نمی‌شود.

> کیفیت با تست و معیار پذیرش سنجیده می‌شود. ادعای «۱۰۰٪ بدون باگ» تضمین فنی نیست.

## گام ۱ — اصلاح قرارداد کلید و امضا

### وضعیت

- اصلاح در مخزن: انجام شده، commit `3d8e9d7`.
- تست سازگاری encoding با PHP واقعی: ۲۰ حالت موفق.
- تست کامل sodium/Ed25519، syntax همهٔ فایل‌های PHP staging، typecheck، lint، ۱۸۵ تست وب و build در CI: موفق.
- اجرای CI: https://github.com/rahmaniho/KarenYar/actions/runs/41279043096
- اعمال روی هاست staging: انجام نشده / منتظر کاربر.
- آزمون واقعی فعال‌سازی و تمدید روی هاست: انجام نشده.
- production: دست‌نخورده.
- گزارش audit وابستگی‌ها در CI تولید می‌شود؛ advisoryهای قبلی هنوز باز هستند و ارتقای وابستگی مرحلهٔ جداگانه دارد.

### مشکل

مرورگر کلید عمومی Ed25519 و امضای refresh را با base64url بدون padding می‌فرستد. نسخهٔ قبلی PHP در activation و refresh از base64 استاندارد سخت‌گیرانه استفاده می‌کرد و کاراکترهای `-` و `_` را رد می‌کرد.

### اصلاح

فایل مشترک `v1/license-encoding.php` اضافه شد. هر دو endpoint اکنون از decoder مشترک استفاده می‌کنند:

- کلید عمومی: دقیقاً 32 بایت.
- امضا: دقیقاً 64 بایت.
- base64url بدون padding پذیرفته می‌شود.
- base64 استاندارد قدیمی، با یا بدون padding، برای سازگاری پذیرفته می‌شود.
- فاصله، خط جدید، padding خراب و بیت‌های انتهایی غیرکانونیکال رد می‌شوند.
- فایل مشترک هیچ secret، دیتابیس یا شبکه‌ای ندارد.

### اعمال روی هاست staging

فقط پوشهٔ زیر تغییر می‌کند:

```text
/home/karensof/public_html/staging.karen-soft.ir/v1/
```

پیش از تغییر، از دو فایل فعلی یک کپی در پوشهٔ خصوصی بگیرید، نه داخل webroot:

```text
/home/karensof/private/karen-staging/backups/
```

سپس:

1. در File Manager فایل `license-encoding.php` را در پوشهٔ `v1` بسازید و محتوای کامل مخزن را قرار دهید.
2. در `activations.php` بعد از `declare(strict_types=1);` این خط را اضافه کنید:

```php
require_once __DIR__ . '/license-encoding.php';
```

3. در `activations.php` بلوک decode کلید عمومی را با نسخهٔ مشترک جایگزین کنید:

```php
$devicePublicKey = karen_license_decode_key_material($devicePublicKeyB64, 32);

if ($devicePublicKey === null) {
    karen_fail(400, 'invalid_device_public_key');
}
```

4. در `refresh.php` همان خط require را بعد از declare اضافه کنید.
5. در `refresh.php` بلوک decode امضا را جایگزین کنید:

```php
$signature = karen_license_decode_key_material($signatureB64, 64);

if ($signature === null) {
    karen_fail(400, 'invalid_signature');
}
```

`bootstrap.php`، کلید خصوصی، دیتابیس، `.htaccess`، پوشهٔ admin و دادهٔ مالی تغییر نمی‌کنند.

### تست گام ۱

تست محلی/CI:

```text
npm run test:license-encoding
npm run test:license-backend
```

تست کامل نیاز به PHP 8.2+ و sodium دارد. CI این تست را با PHP 8.3 اجرا می‌کند. تست‌ها شامل کلید/امضای واقعی Ed25519، نسخهٔ base64url، نسخهٔ استاندارد قدیمی، طول اشتباه، padding خراب و امضای دست‌کاری‌شده هستند.

بعد از اعمال روی هاست، باید یک فعال‌سازی و یک تمدید واقعی از کلاینت مرورگر انجام شود. صرف پاسخ `method_not_allowed` به GET، تست قبولی POST نیست.

## گام‌های بعدی، به ترتیب

### گام ۲ — اعتماد کلاینت به issuer

- دریافت کلید عمومی issuer از مسیر ادمین محافظت‌شده، بدون نمایش کلید خصوصی.
- پین کردن کلید عمومی در بیلد staging.
- بررسی دقیق `iss`، `aud`، `env`، `kid`، محصول و دستگاه.
- تست توکن issuer/audience اشتباه و کلید ناسازگار.

### گام ۳ — پایداری سرور

- ترتیب ثابت قفل license سپس device در activation/refresh/admin.
- تست همزمانی سقف دستگاه.
- تست replay و انقضای nonce.
- یکدست‌سازی خطاهای لغو دستگاه/لایسنس.
- پاک‌سازی nonce بدون افزایش بی‌دلیل تراکنش.

### گام ۴ — پنل مدیریت و گزارش

- مرور لایسنس‌ها، دستگاه‌ها و رویدادها با صفحه‌بندی و فیلتر.
- صدور لایسنس با کد یک‌بارنمایش.
- لغو/فعال‌سازی دستگاه با تأیید و ثبت actor.
- گزارش رویدادها بدون نمایش secret یا دادهٔ مالی.
- حذف installerها و صفحات تست از webroot پس از تأیید.

### گام ۵ — حساب کاربری، بدون بکاپ ابری

- حساب کاربری فقط برای هویت، مجوز و دستگاه‌ها.
- ورود امن و مدیریت نشست.
- اتصال لایسنس به حساب در صورت نیاز.
- بکاپ همچنان فایل محلی روی دستگاه/کامپیوتر کاربر.
- هیچ endpoint آپلود بکاپ مالی یا sync در این مرحله اضافه نمی‌شود.

### گام ۶ — پذیرش staging و سپس production

- تست end-to-end فعال‌سازی، تمدید، لغو، سقف دستگاه و حالت آفلاین.
- تست بازیابی بکاپ محلی روی دستگاه دوم.
- بررسی لاگ، نرخ خطا، backup دیتابیس لایسنس و rollback.
- production فقط پس از قبولی staging.

## معیار تحویل نهایی محدودهٔ لایسنس

- فعال‌سازی و تمدید واقعی مرورگر موفق.
- دستگاه لغوشده تمدید نمی‌گیرد.
- سقف دستگاه در درخواست همزمان نقض نمی‌شود.
- nonce تکراری رد می‌شود.
- توکن جعلی/محیط اشتباه/کلید اشتباه رد می‌شود.
- خطای شبکه یا rate limit موقت، دادهٔ کاربر را پاک نمی‌کند.
- پنل ادمین بدون احراز هویت باز نمی‌شود.
- رویدادهای مهم قابل ردیابی‌اند.
- فایل مالی و بکاپ کاربر به سرور ارسال نمی‌شود.
- صفحات تست/installer عمومی باقی نمی‌مانند.
- CI و تست‌های پذیرش staging سبز هستند.
