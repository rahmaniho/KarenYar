# راهنمای گام‌به‌گام امنیت و کاهش کپی حساب‌یار

این راهنما بر اساس کد فعلی مخزن نوشته شده است؛ **گزارش تست نفوذ سایت زنده نیست**. اجرای مراحل، تغییر در انتشار تولید و مهاجرت داده‌ها باید ابتدا روی محیط آزمایشی انجام شود. هیچ کلید واقعی یا تغییر امنیتی در زمان تهیهٔ این راهنما تولید یا اعمال نشده است.

## هدف را درست تعریف کنیم

- HTML، CSS، JavaScript و تصاویری که مرورگر دریافت می‌کند قابل کپی هستند؛ ضدکپی صددرصدی وجود ندارد.
- هدف عملی: کپی ظاهر، بدون کلید خصوصی، حساب معتبر و سرویس شما نتواند لایسنس معتبر بسازد یا از امکانات سروری استفاده کند.
- امنیت اطلاعات مالی، کنترل اشتراک و مالکیت معنوی سه موضوع جدا هستند و هرکدام کنترل‌های خود را دارند.
- انقضای لایسنس نباید دسترسی کاربر به داده‌های خودش، خروجی گرفتن یا پشتیبان‌گیری را از بین ببرد.

## وضعیت فعلی که باید اصلاح شود

| موضوع      | مشاهده در مخزن                                                                          | نتیجه                                                                                         |

## گام ۱ — محیط آزمایشی و نسخهٔ قابل بازگشت بسازید

1. یک محیط آزمایشی جدا از دامنه و دادهٔ مشتریان بسازید؛ دادهٔ واقعی را برای آزمایش کپی نکنید.
2. مسیر انتشار فعلی، دسترسی‌های دامنه/هاست، متغیرهای محیطی و روش ساخت APK را ثبت کنید.
3. از نسخهٔ فعلی خروجی پشتیبان بگیرید و **بازیابی آن را در محیط آزمایشی امتحان کنید**. پشتیبان فعلی رمزنگاری‌شده نیست؛ فایل را در فضای دسترسی‌محدود نگه دارید.
4. تغییرات را در تغییرهای کوچک و قابل بازگشت انجام دهید؛ هم‌زمان لایسنس، رمزنگاری و هاست را عوض نکنید.
5. برای کاربران فعلی، برنامهٔ مهاجرت و پشتیبانی تعیین کنید؛ ارتقا نباید موجب از دست رفتن اطلاعات یا قطع ناگهانی اشتراک معتبر شود.

**معیار پذیرش:** نسخهٔ آزمایشی قابل بازیابی است و فهرست کاربران/دستگاه‌هایی که به مهاجرت نیاز دارند مشخص است.

## گام ۲ — محرمانه‌ها را از خروجی وب خارج کنید

1. در تنظیمات CI/CD و هاست بررسی کنید آیا `VITE_LICENSE_SECRET` استفاده شده است یا خیر. وجود واقعی آن در انتشار زنده باید جداگانه بررسی شود.
2. هیچ محرمانهٔ امضا، رمز دیتابیس، توکن مدیریتی یا کلید خصوصی را در متغیر `VITE_*` قرار ندهید. این متغیرها برای اطلاعات عمومی سمت مرورگرند.
3. مقدار پیش‌فرض دمو و کلیدهای نمونهٔ README را از فرایند فروش واقعی کنار بگذارید.
4. اگر محرمانهٔ HMAC قبلاً منتشر شده، آن را **لو رفته فرض کنید**. صرفاً ساختن کلید با یک محرمانهٔ جدید، معماری آسیب‌پذیر را اصلاح نمی‌کند.
5. صدور لایسنس جدید را به سرویس فروشنده منتقل کنید. برای کاربران قدیمی، لایسنس جایگزین و مهلت مهاجرت تعیین کنید؛ سپس پذیرش لایسنس قدیمی را پایان دهید.
6. الگوهای زیر را به `.gitignore` اضافه کنید؛ فایل‌هایی که قبلاً توسط Git رهگیری شده‌اند با ignore از تاریخچه حذف نمی‌شوند:

```gitignore
.env.*
!.env.example
*.pem
*.key
secrets/
```

7. دسترسی مخزن، پنل هاست، CI و سرویس صدور را محدود کنید. برای مدیران، ورود دومرحله‌ای و محیط انتشار دارای تأیید فعال کنید.

**فایل‌های مرتبط:** `.env.example`، `.gitignore`، تنظیمات CI، `scripts/generate-license.mjs`، README.

**معیار پذیرش:** در خروجی جدید، محرمانهٔ واقعی وجود ندارد؛ کلید خصوصی در مخزن/Artifact عمومی نیست؛ کلیدهای دمو در نسخهٔ تجاری پذیرفته نمی‌شوند.

## گام ۳ — لایسنس را به امضای نامتقارن مهاجرت دهید

### معماری

- سرور فروشنده: نگهداری کلید خصوصی، بررسی اشتراک و صدور مجوز امضاشده.
- مرورگر: فقط کلید عمومی و بررسی امضا؛ کلید عمومی secret نیست.
- الگوریتم پیشنهادی: Ed25519، مشروط به پشتیبانی مرورگرهای هدف. برای WebViewهای قدیمی، سازگاری WebCrypto را آزمایش کنید؛ در صورت نیاز از RSA-PSS با SHA-256 و طول کلید مناسب استفاده کنید.
- امضای اندروید، امضای لایسنس و رمزنگاری داده سه کلید مستقل هستند.

### تولید کلید آزمایشی

این دستور را در فضای امن فروشنده و **خارج از پوشهٔ عمومی سایت** اجرا کنید. برای تولید کلید واقعی، فرایند نگهداری کلید در Secret Manager/KMS یا ماژول سخت‌افزاری امن (HSM) را به کار ببرید:

```bash
umask 077
openssl genpkey -algorithm ed25519 -out license-private-key.pem
openssl pkey -in license-private-key.pem -pubout -out license-public-key.pem
chmod 600 license-private-key.pem
```

کلید خصوصی را commit نکنید، در پیام‌رسان نفرستید و وارد متغیرهای build سمت مرورگر نکنید. کلید عمومی را می‌توان همراه برنامه منتشر کرد.

### اطلاعات مجوز

اطلاعات شخصی غیرضروری را داخل مجوز نگذارید. نمونهٔ ساختار:

```json
{
  "iss": "hesabyar-license-server",
  "aud": "hesabyar-app",
  "sub": "customer-opaque-id",
  "jti": "license-id",
  "plan": "pro",
  "features": ["backup", "pdf-export"],
  "iat": 1787356800,
  "exp": 1787961600,
  "deviceKeyId": "registered-device-key-id"
}
```

- `iat` و `exp` زمان یونیکس هستند؛ اعتبار توکن را کوتاه کنید، مثلاً ۷ تا ۱۴ روز برای مجوز آفلاین. تاریخ پایان قرارداد اشتراک را جدا از عمر توکن نگه دارید.
- سرور باید وضعیت لغو، پایان اشتراک و محدودیت دستگاه را بررسی کند؛ سپس توکن تازه صادر کند.
- امضا روی بایت‌های دقیق پیام باشد، نه JSON بازسازی‌شده هنگام بررسی.
- یک شناسهٔ کلید `kid` برای چرخش کلید داشته باشید؛ فقط کلیدهای عمومی مورد اعتماد برنامه قابل استفاده باشند.

### نمونهٔ هستهٔ امضا در Node.js

این نمونه فقط امضاست؛ سرویس صدور هنوز به احراز هویت، کنترل دسترسی، اعتبارسنجی و ثبت رویداد نیاز دارد:

```js
import { createPrivateKey, sign } from 'node:crypto';

const b64url = (value) => Buffer.from(value).toString('base64url');

function signLicense(claims, privateKeyPem, kid) {
  const header = { alg: 'EdDSA', typ: 'hesabyar-license', kid };
  const message = `${b64url(JSON.stringify(header))}.${b64url(JSON.stringify(claims))}`;
  const key = createPrivateKey(privateKeyPem);
  const signature = sign(null, Buffer.from(message), key);
  return `HY2.${message}.${signature.toString('base64url')}`;
}
```

### بررسی در برنامه

1. تعداد بخش‌ها و قالب `HY2` را بررسی کنید.
2. الگوریتم مورد انتظار را از سیاست برنامه تعیین کنید؛ به الگوریتم دلخواه ورودی اعتماد نکنید.
3. `kid` را فقط در فهرست کلیدهای مجاز پیدا کنید.
4. امضای بخش header.payload را با WebCrypto بررسی کنید.
5. ساختار و نوع claims، صادرکننده، مخاطب، زمان صدور و انقضا را اعتبارسنجی کنید.
6. سطح دسترسی را از claims معتبر بگیرید، نه از تنظیمات قابل تغییر localStorage.
7. در اتصال بعدی، وضعیت لغو و اشتراک را از سرور بگیرید.

**محدودیت حالت آفلاین:** در حالت کاملاً آفلاین، دست‌کاری کد یا ساعت دستگاه و لغو فوری را نمی‌توان به‌طور قطعی کنترل کرد. دورهٔ آفلاین محدود و اتصال دوره‌ای، ریسک را کاهش می‌دهد نه اینکه آن را صفر کند.

**معیار پذیرش:** تغییر یک بایت، کلید ناشناس، انقضا و اشتراک لغوشده پس از اتصال رد شوند؛ کاربر همچنان بتواند دادهٔ خودش را بخواند و خروجی بگیرد.

## گام ۴ — سرویس لایسنس را واقعاً کنترل‌کننده کنید

داشتن endpoint صدور به‌تنهایی کافی نیست. حداقل مسیرها:

| مسیر                                 | کار                            | کنترل ضروری                                          |
| ------------------------------------ | ------------------------------ | ---------------------------------------------------- |
| `POST /v1/activations`               | مصرف کد فعال‌سازی و ثبت دستگاه | کد محدود/یک‌بارمصرف، محدودیت تلاش، احراز هویت متناسب |
| `POST /v1/license/refresh`           | دریافت مجوز کوتاه‌عمر          | حساب معتبر، دستگاه مجاز، اشتراک فعال                 |
| `GET /v1/entitlements`               | وضعیت فعلی امکانات             | مجوز همان مشتری، پاسخ خصوصی                          |
| `POST /v1/admin/licenses/:id/revoke` | لغو اشتراک                     | نقش مدیر، MFA، ثبت دلیل و رویداد                     |

اصول اجرا:

- کد فعال‌سازی را در دیتابیس به‌صورت خام نگه ندارید؛ مقدار هش‌شده و وضعیت مصرف را ذخیره کنید.
- برای محدودیت دستگاه، ترجیحاً کلید نامتقارن دستگاه را ثبت کنید و چالش سرور را با آن امضا بگیرید. اثر انگشت مرورگر به‌تنهایی اثبات مالکیت نیست.
- سقف دستگاه و مصرف کد را در تراکنش دیتابیس کنترل کنید تا درخواست هم‌زمان از سقف عبور نکند.
- کلید خصوصی دستگاه را با WebCrypto به‌صورت non-extractable بسازید و در IndexedDB نگه دارید. این کار کپی سادهٔ کلید را سخت‌تر می‌کند، اما XSS یا دستگاه آلوده را بی‌اثر نمی‌کند.
- عملیات پولی مهم را سمت سرور انجام دهید. اگر همهٔ منطق فقط در مرورگر باشد، بررسی لایسنس سمت کلاینت قابل حذف است.
- برای سرویس، محدودیت نرخ، لاگ حسابرسی، پشتیبان و مسیر بازیابی کلید داشته باشید.
- توکن لایسنس را جای نشست کاربر یا مجوز دسترسی به دادهٔ مشتری استفاده نکنید.

**معیار پذیرش:** درخواست مشتری A برای لایسنس/دادهٔ مشتری B رد شود؛ مدیر بدون ورود دومرحله‌ای نتواند کلید صادر کند؛ درخواست هم‌زمان سقف دستگاه را نشکند.

## گام ۵ — HTTPS و هدرهای امنیتی را روی هاست واقعی اعمال کنید

1. ابتدا مشخص کنید سایت واقعاً از Pages، Vercel، Apache یا سرویس دیگری منتشر می‌شود.
2. HTTPS اجباری و سلامت گواهی را بررسی کنید. در Pages گزینهٔ **Enforce HTTPS** را در تنظیمات پروژه بررسی کنید.
3. GitHub Pages را نباید قابلیت تنظیم هدر سفارشی دلخواه فرض کرد. برای CSP و هدرهای پاسخ، از هاست/CDN با پشتیبانی هدر استفاده کنید؛ تغییر `.htaccess` به‌تنهایی روی Pages اثر ندارد.
4. هدرهای پایه:

```text
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(self), microphone=(), geolocation=()
```

دوربین برای بارکدخوان لازم است؛ آن را ناخواسته غیرفعال نکنید.

5. CSP را ابتدا **Report-Only** و متناسب با خروجی واقعی Vite آزمایش کنید. نقطهٔ شروع پیشنهادی، نه تنظیم تضمین‌شده برای همهٔ هاست‌ها:

```text
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  font-src 'self';
  img-src 'self' data: blob:;
  connect-src 'self' https://YOUR-LICENSE-API.example;
  worker-src 'self';
  manifest-src 'self';
  object-src 'none';
  base-uri 'self';
  form-action 'self';
  frame-ancestors 'none'
```

این نمونه یک خط هدر است؛ آدرس API را با دامنهٔ واقعی جایگزین کنید. فونت‌های فعلی محلی‌اند. inline style برای کتابخانه‌های نمودار/انیمیشن ممکن است لازم باشد؛ آن را با اجرای JavaScript دلخواه یکسان ندانید. پس از رفع گزارش‌ها و تست PDF، بارکد، نصب PWA و آفلاین، CSP را enforcing کنید. `frame-ancestors` باید به‌صورت هدر پاسخ بیاید، نه meta.

6. HSTS را ابتدا با عمر کوتاه آزمایش کنید. `includeSubDomains` فقط وقتی مناسب است که همهٔ زیردامنه‌ها HTTPS داشته باشند؛ preload را بدون بررسی تعهد بلندمدت فعال نکنید.
7. HTML، سرویس‌ورکر و مانیفست را سریع بازاعتبارسنجی کنید؛ دارایی‌های نام‌گذاری‌شده با hash می‌توانند کش بلندمدت داشته باشند. پاسخ حساب، لایسنس و اطلاعات خصوصی باید `Cache-Control: no-store` باشد.

**بررسی:** در ابزار Network مرورگر، هدر پاسخ سند اصلی و API را ببینید؛ وجود دستور در فایل مخزن اثبات اعمال‌شدن آن روی سایت نیست.

**معیار پذیرش:** HTTPS سالم، هدرها روی پاسخ واقعی، نبود خطای CSP در مسیرهای اصلی و عدم کش‌شدن پاسخ خصوصی.

## گام ۶ — اگر حساب آنلاین اضافه می‌کنید، احراز هویت و مجوز را سروری کنید

این مرحله برای سرویس آنلاین آینده است؛ برنامهٔ آفلاین فعلی حساب سروری ندارد.

1. رمزهای کاربری را با کتابخانهٔ معتبر و Argon2id و پارامترهای به‌روز و بنچمارک‌شده هش کنید؛ SHA-256 ساده مناسب ذخیرهٔ رمز نیست.
2. نشست را با کوکی `HttpOnly`، `Secure` و `SameSite` متناسب با معماری دامنه‌ها مدیریت کنید. توکن نشست بلندعمر را در localStorage نگذارید.
3. اگر کوکی برای احراز هویت استفاده می‌شود، CSRF و بررسی Origin را جدی بگیرید. CORS جای احراز هویت یا CSRF را نمی‌گیرد.
4. برای ورود، بازیابی رمز و فعال‌سازی، محدودیت نرخ بر اساس حساب و IP، پیام خطای غیرافشاگر و امکان MFA داشته باشید.
5. شناسهٔ فروشگاه/مشتری را از نشست معتبر بگیرید. هر پرس‌وجو باید به tenant همان کاربر محدود شود؛ مقدار `tenantId` ارسالی مرورگر کافی نیست.
6. برای هر خواندن/ویرایش فاکتور، حساب، کالا و پشتیبان، مالکیت منبع را بررسی کنید. آزمون IDOR/BOLA ضروری است.
7. مبلغ، مالیات، موجودی و مجوز قابلیت را سمت سرور اعتبارسنجی کنید. ثبت فروش باید اتمیک و دارای کلید idempotency یکتا در محدودهٔ فروشگاه باشد.
8. لاگ ورود، تغییر نقش، صدور/لغو لایسنس و عملیات حساس را نگه دارید؛ رمز، کوکی، کلید و محتوای کامل پشتیبان را لاگ نکنید.

**معیار پذیرش:** آزمون دسترسی متقاطع دو فروشگاه شکست بخورد؛ جعل مبلغ/نقش از مرورگر اثر نداشته باشد؛ نشست پس از خروج در سرور بی‌اعتبار شود.

## گام ۷ — پشتیبان‌ها را پیش از کل دیتابیس رمزنگاری کنید

این کار محدودهٔ تغییر کمتری دارد و نقطهٔ شروع مناسبی است.

1. یک قالب نسخه‌دار مانند `HYBKP1` تعریف کنید که الگوریتم، نسخه، salt، nonce و پارامترهای KDF را مشخص کند.
2. از رمز عبور قوی کاربر و KDF معتبر مانند Argon2id برای مشتق‌سازی کلید استفاده کنید. اگر فقط WebCrypto در دسترس است، PBKDF2 با پارامتر مطابق راهنمای روز و بنچمارک دستگاه هدف انتخاب شود؛ iterations را عددی دائمی و تضمین‌شده فرض نکنید.
3. محتوا را با AES-256-GCM رمز کنید. salt تصادفی و nonce تصادفی ۹۶ بیتی برای هر عملیات بسازید؛ **زوج کلید و nonce هرگز تکرار نشود**.
4. نسخه و مشخصات قالب را به‌عنوان additional authenticated data تأیید کنید؛ ciphertext و tag را نگه دارید.
5. رمز را داخل فایل یا کنار آن ذخیره نکنید. کلید بازیابی جداگانه و هشدار فراموشی رمز را در UX مشخص کنید.
6. پیش از جایگزینی دادهٔ فعلی، رمزگشایی، احراز اصالت و اعتبارسنجی کامل ساختار انجام شود. برای اندازهٔ فایل، تعداد سطرها، نوع مبلغ/تاریخ و شناسه‌ها محدودیت بگذارید.
7. بازیابی باید مثل رفتار فعلی اتمیک بماند؛ شکست نباید دیتابیس فعلی را نیمه‌پاک کند.
8. پشتیبان قدیمی همچنان با اعلام روشن قابل ورود باشد، اما خروجی جدید پیش‌فرض رمزنگاری‌شده باشد. مهاجرت را اجباری و بی‌اطلاع انجام ندهید.

**فایل‌های مرتبط در مرحلهٔ اجرا:** `src/core/db/backup.ts`، تست‌های backup، صفحهٔ تنظیمات و ابزار جدید رمزنگاری با کتابخانهٔ بررسی‌شده.

**معیار پذیرش:** فایل با متن‌خوان قابل جستجو نباشد؛ رمز غلط و فایل دست‌کاری‌شده رد شوند؛ بازیابی رمز صحیح برابر دادهٔ اولیه باشد؛ شکست وسط بازیابی داده را خراب نکند.

## گام ۸ — رمزنگاری دادهٔ محلی و مهاجرت پین را جداگانه اجرا کنید

1. مدل تهدید را مشخص کنید: سرقت دستگاه خاموش، مرورگر باز، XSS و کاربر دارای دسترسی سیستم یکسان نیستند. رمزنگاری، دستگاه آلوده یا برنامهٔ بازِ دارای کلید در حافظه را کاملاً امن نمی‌کند.
2. یک کلید دادهٔ تصادفی بسازید و آن را با کلید مشتق از رمز قوی کاربر بپوشانید؛ envelope encryption تغییر رمز را ساده‌تر می‌کند.
3. برای هر رکورد/بخش، nonce یکتا و دادهٔ زمینه مانند جدول، شناسه و نسخهٔ schema را به احراز اصالت اضافه کنید.
4. فیلدهایی که برای جستجو index می‌شوند ممکن است نشت اطلاعات داشته باشند؛ تصمیم دربارهٔ فیلدهای searchable را مستند کنید.
5. کلید بازکردن داده را فقط تا زمان بازبودن قفل در حافظه نگه دارید. با قفل‌شدن، دسترسی برنامه به کلید پاک شود؛ صفرشدن تضمینی همهٔ کپی‌های حافظه در JavaScript ممکن نیست.
6. پین کوتاه را محافظ اصلی فایل آفلاین معرفی نکنید. برای رمزنگاری، رمز قوی یا کلید بازیابی لازم است؛ پین می‌تواند نقش راحتی در کنار آن داشته باشد.
7. مهاجرت schema را نسخه‌دار و تراکنشی کنید: پشتیبانِ قابل بازیابی، تبدیل، بررسی تعداد و محتوای داده، سپس تأیید. تا موفقیت کامل، مسیر بازگشت را نگه دارید.
8. در خطای رمزگشایی، مخفیانه به دادهٔ plaintext برنگردید و دیتابیس را خودکار پاک نکنید.

**فایل‌های مرتبط:** `src/core/db/db.ts`، `src/core/utils/pin.ts`، `src/store/settings-store.ts`، `src/components/LockScreen.tsx` و تست‌های مهاجرت.

**معیار پذیرش:** دادهٔ حساس در حالت قفل بدون کلید قابل خواندن نباشد؛ نسخهٔ قدیمی بدون حذف داده ارتقا یابد؛ رمز اشتباه باعث پاک‌شدن اطلاعات نشود.

## گام ۹ — PWA، زنجیرهٔ تأمین و انتشار را کنترل کنید

- پاسخ‌های احراز هویت، لایسنس و دادهٔ مشتری را در Cache Storage ذخیره نکنید. مسیرهای API را صریحاً از precache و navigation fallback جدا کنید.
- به‌روزرسانی سرویس‌ورکر را آزمایش کنید؛ کاربر نباید پس از رفع آسیب‌پذیری برای مدت نامعلوم کد قدیمی بگیرد.
- انتشار وب و APK را جدا نگه دارید. کلید Release اندروید را در Secretهای محافظت‌شدهٔ CI نگه دارید؛ امضای APK ضدکپی لایسنس نیست.
- نسخهٔ Node ورک‌فلو را با نسخهٔ پشتیبانی‌شدهٔ پروژه هماهنگ کنید؛ README نسخهٔ ۲۲+ را اعلام کرده ولی workflow بررسی‌شده از ۲۰ استفاده می‌کند.
- از `npm ci` و lockfile استفاده کنید. `npm audit` را در CI اجرا کنید؛ `npm audit fix --force` را بدون بررسی تغییرات ناسازگار اجرا نکنید.
- Secret scanning، بررسی وابستگی‌ها، حداقل دسترسی workflow و بازبینی تغییرات CI را فعال کنید. Actionها را به نسخهٔ مشخص و ترجیحاً commit SHA ثابت کنید.
- در ساخت انتشار، آرشیوها، `.env`، فایل‌های کلید و گزارش‌های دارای اطلاعات خصوصی را منتشر نکنید.
- minification و نبود sourcemap عمومی را حفظ کنید؛ obfuscation سنگین را جای کنترل سرور و امنیت داده نگذارید.
- برای انتشار تجاری، شرایط استفاده، قرارداد، ثبت برند و مسیر رسیدگی به کپی‌برداری داشته باشید. واترمارک می‌تواند به شناسایی نسخهٔ نشت‌کرده کمک کند، نه جلوگیری قطعی.

## گام ۱۰ — آزمون کنید و بعد منتشر کنید

### آزمون‌های خودکار ضروری

- لایسنس: امضای معتبر، تغییر payload، کلید ناشناس، `kid` ناشناس، انقضا، نسخهٔ قالب، لغو پس از اتصال و دورهٔ آفلاین.
- سرویس: محدودیت تلاش، مصرف هم‌زمان کد، سقف دستگاه، نقش مدیر و دسترسی متقاطع مشتری‌ها.
- رمزنگاری: رمز غلط، nonce متفاوت، ciphertext دست‌کاری‌شده، قالب ناسازگار و فایل بیش‌ازحد بزرگ.
- مهاجرت: دادهٔ قدیمی، قطع عملیات وسط تبدیل، rollback و حفظ تعداد/مبالغ رکوردها.
- وب: ورود، فاکتور، PDF، بارکد، حالت آفلاین، به‌روزرسانی PWA و خروج/ورود مجدد.
- دسترسی‌پذیری و موبایل: صفحهٔ قفل، هشدار فراموشی رمز و بازیابی با صفحه‌کلید و نمایشگر کوچک.

دستورهای موجود پروژه برای بررسی رگرسیون:

```bash
npm ci
npm run typecheck
npm run lint
npm test
npm run build
npm run test:e2e
npm run test:android-release
```

این دستورها به‌تنهایی تست نفوذ نیستند. پیش از فروش گسترده، بازبینی مستقل امنیت سرویس لایسنس، API و رمزنگاری انجام دهید.

### چک‌لیست خروج نسخه

- [ ] کلید خصوصی و محرمانه در خروجی مرورگر و مخزن عمومی نیست.
- [ ] لایسنس‌های دمو از مسیر تجاری جدا شده‌اند و مهاجرت مشتریان مشخص است.
- [ ] کنترل اشتراک و مجوز روی سرور آزمون شده است.
- [ ] هدرها روی پاسخ هاست واقعی دیده می‌شوند، نه فقط در فایل تنظیمات.
- [ ] دادهٔ خصوصی در کش مرورگر یا لاگ نیست.
- [ ] پشتیبان رمزنگاری‌شده و بازیابی موفق آزمایش شده است.
- [ ] رمز اشتباه یا انقضای لایسنس موجب حذف دادهٔ کاربر نمی‌شود.
- [ ] مسیر بازگشت انتشار و مسئول پاسخ‌گویی حادثه مشخص است.
