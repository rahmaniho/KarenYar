# نقشهٔ راه: حرفه‌ای‌تر شدن و تجاری‌سازی کارو

این سند پیشنهادهای عملی برای «نسخهٔ سروری کارو» است: از یک بک‌اند کارآمد به یک
محصول قابل‌فروش. هر بند با «چرا» و «کار لازم» آمده تا بتوان مستقیم به بک‌لاگ
تبدیل شود.

---

## بخش الف — حرفه‌ای‌تر شدن محصول

### ۱) حسابرسی و تاریخچه ✅ (انجام‌شده در همین شاخه)

`audit_logs` + `AuditLogger` + پنل «رویدادهای اخیر» در پنل مدیر: ورود/خروج،
ورود ناموفق، ساخت/ویرایش/حذف فروشگاه، تغییر لایسنس، انتقال داده و پاک‌سازی.
**بعدی:** نمایش رویدادهای فروشگاه در تنظیمات خود مشتری و خروجی CSV برای حسابرس.

### ۲) چند کاربر در هر فروشگاه + نقش‌های دقیق

الان هر فروشگاه یک حساب دارد. برای فروشگاه واقعی حداقل سه نقش لازم است:

| نقش      | دسترسی                                |
| -------- | ------------------------------------- |
| مالک     | همه‌چیز + مدیریت کاربران و لایسنس     |
| صندوقدار | صندوق فروش، فاکتور، مشاهدهٔ کالا      |
| انباردار | کالا، موجودی، گردش انبار              |
| حسابدار  | گزارش‌ها، مشتریان، بدهی‌ها (بدون حذف) |

**کار لازم:** جدول `store_users` (many-to-many) + `role` در pivot، میدل‌ور
`can:…`، تغییر `store_id` از روی کاربر به عضویت، و لاگ حسابرسی برای هر نقش.

### ۳) آفلاین در نسخهٔ سروری (مهم‌ترین شکاف)

فروشگاه‌ها اینترنت پایدار ندارند؛ نسخهٔ وبِ لاراول همین حالا بدون شبکه کار
نمی‌کند. مسیر پیشنهادی:

1. سرویس‌ورکر + کش اپ‌شل (Vite PWA) با `navigateFallbackDenylist` برای `/api`.
2. صف عملیات در IndexedDB (Outbox) و ارسال خودکار پس از اتصال.
3. استفاده از همان قرارداد `rev`/`baseRev` که در sync پیاده شده.

### ۴) فاکتور رسمی و چاپ حرفه‌ای

- شماره‌گذاری بدون شکاف (`invoice_counters` با قفل تراکنشی).
- QR فاکتور (لینک مشاهدهٔ عمومی با توکن امضاشده) و مهر/امضای دیجیتال.
- قالب‌های چاپی قابل انتخاب + خروجی PDF/A.
- ارسال فاکتور با پیامک/واتساپ/ایمیل (سرویس کاوه‌نگار/ملی‌پیامک).

### ۵) انبار حرفه‌ای

چند انباره، انتقال بین انبارها، شمارش دوره‌ای (stocktake)، سریال/بچ و تاریخ
انقضا برای کالاهای حساس.

### ۶) سند حسابداری سبک

اگر هدف بازار بزرگ‌تر است: دفتر روزنامه/کل با کدینگ استاندارد و گزارش‌های
«ترازنامه/سود و زیان» — با نگاشت خودکار از فاکتور و پرداخت.

### ۷) پشتیبان‌گیری و بازیابی

دستور `php artisan karo:backup` (دیتابیس + storage) با نگه‌داشت N نسخه روی
S3/فضای هاست + مسیر بازگردانی در پنل مدیر.

### ۸) اعلان‌ها

- مدیر: لایسنس‌های نزدیک انقضا (۳۰/۷ روز)، فروشگاه‌های غیرفعال.
- فروشگاه: موجودی زیر حد، بدهی سررسیدشده، خطای همگام‌سازی.
  کانال: درون‌برنامه‌ای + ایمیل + پیامک اختیاری.

### ۹) امنیت

| مورد                        | وضعیت   | اقدام                                        |
| --------------------------- | ------- | -------------------------------------------- |
| نشست + CSRF + throttle ورود | ✅ دارد | —                                            |
| ۲FA برای مدیر               | ❌      | TOTP + کد پشتیبان                            |
| سیاست رمز و چرخهٔ اجباری    | ❌      | حداقل ۸ کاراکتر + انقضای ۱۸۰ روز             |
| محدود کردن پنل مدیر به IP   | ❌      | allowlist اختیاری                            |
| رمزنگاری فیلدهای حساس       | ❌      | `encrypted` cast برای تلفن/آدرس در صورت نیاز |
| دفتر رویداد                 | ✅ دارد | خروجی CSV + هشدار ورود ناموفق مکرر           |

### ۱۰) کیفیت و انتشار

- CI روی `main` برای `npm test`/`lint` (الان فقط build اجرا می‌شود) + e2e.
- پوشش تست بک‌اند برای مسیرهای پول (فاکتور، پرداخت، دستمزد).
- نسخه‌بندی معنایی + CHANGELOG + مهاجرت داده با `artisan migrate` بدون توقف.
- تحلیل استاتیک PHP (PHPStan) و Pint در CI.

### ۱۱) کارایی

- pull صفحه‌بندی‌شده برای فروشگاه‌های بزرگ (الان همهٔ تغییرات یک‌جا می‌آید).
- ایندکس مرکب `(store_id, rev)` روی جدول‌های سنگین.
- صف برای import بزرگ (`data_imported` را به Job ببریم).
- کش گزارش‌های داشبورد (۶۰ ثانیه) برای کاهش فشار دیتابیس.

## بخش ب — تجاری‌سازی

### ۱) بسته‌بندی و قیمت‌گذاری پیشنهادی

| بسته                   | چه دارد                                                                | مدل قیمت                   |
| ---------------------- | ---------------------------------------------------------------------- | -------------------------- |
| **رایگان**             | یک فروشگاه، ۱۰۰ فاکتور در ماه، PDF با واترمارک، بدون پشتیبانی          | همیشگی                     |
| **حرفه‌ای (pro)**      | فروشگاه نامحدود در یک لایسنس، فاکتور نامحدود، گزارش‌ها، دو کاربر       | سالانه per فروشگاه         |
| **حرفه‌ای+ (proplus)** | کاربر نامحدود، انبار چندگانه، پشتیبان‌گیری خودکار، پشتیبانی اولویت‌دار | سالانه + افزودنی           |
| **مادام‌العمر**        | همان proplus برای همیشه، پشتیبانی یک‌ساله                              | یک‌باره (۳–۴ برابر سالانه) |

نکته: مدل داده همین حالا آماده است (`tiers: pro/proplus`, `is_lifetime`,
`expires_at`) — فقط تعریف قابلیت‌ها در `license-core.ts` و قیمت‌گذاری می‌ماند.

### ۲) جریان فروش و پرداخت

1. صفحهٔ «قیمت‌ها» + ثبت‌نام خودکار فروشگاه (self-service) روی همان
   `POST /api/manager/stores` که مدیر استفاده می‌کند (با محدودیت نرخ).
2. درگاه پرداخت (زرین‌پال/آیدی‌پی) → webhook تأیید → فعال‌سازی/تمدید لایسنس
   - ثبت رویداد در `audit_logs`.
3. صورتحساب و تمدید خودکار + یادآوری ایمیلی/پیامکی پیش از انقضا.
4. کد تخفیف و پلن سازمانی (چند فروشگاه زیر یک حساب).

### ۳) سه مدل استقرار = سه بخش بازار

| مدل                | مخاطب                 | چگونه                                                 |
| ------------------ | --------------------- | ----------------------------------------------------- |
| **ابری (SaaS)**    | فروشگاه کوچک          | ما میزبانی می‌کنیم؛ اشتراک ماهانه                     |
| **روی هاست مشتری** | کسب‌وکار حساس به داده | بستهٔ ZIP + لایسنس سالانه (همین `deploy/laravel-app`) |
| **اندروید آفلاین** | بازار بدون اینترنت    | APK + لایسنس آفلاین امضاشده                           |

### ۴) کنترل لایسنس و ضد دور زدن

- سرور صدور لایسنس (داریم) + heartbeat دوره‌ای از کلاینت.
- مهلت مودبانه (grace ۱۴ روزه) برای قطعی اینترنت.
- امضای Ed25519 لایسنس‌های آفلاین (زیرساخت آن در `src/core/license` هست).
- قفل نرم: انقضا هرگز دسترسی به داده‌های خودِ کاربر را نمی‌بندد (قرارداد فعلی).

### ۵) اعتماد، انطباق و پشتیبانی

- رعایت الزامات مالیاتی (ارزش افزوده، صورت معاملات فصلی؛ آماده‌سازی برای
  سامانهٔ مؤدیان).
- سیاست نگه‌داری داده، امکان خروجی کامل داده (data portability) و حذف حساب.
- SLA مکتوب برای بستهٔ proplus + کانال تیکت داخل اپ.
- مستندات فارسی گام‌به‌گام + ویدیوهای ۲ دقیقه‌ای + دموی آنلاین با دادهٔ نمونه.

### ۶) بازاریابی و رشد

- دموی زندهٔ عمومی (`demo.karo.…`) با دادهٔ نمایشی و بازنشانی روزانه.
- صفحهٔ مقایسه با رقبا (هلو/سپیدار/نرم‌افزارهای ابری).
- برنامهٔ معرفی (referral) — حتی ساده: یک ماه رایگان برای هر معرفی.
- محتوای آموزشی: «چطور موجودی انبار را کنترل کنیم» و… با CTA به ثبت‌نام.

### ۷) سنجه‌هایی که باید از روز اول اندازه بگیریم

| سنجه                        | چرا                     |
| --------------------------- | ----------------------- |
| نرخ تبدیل trial → paid      | سلامت قیف فروش          |
| زمان تا اولین فاکتور (TTFV) | ساده بودن محصول         |
| ماندگاری ۳۰/۹۰ روزه         | ارزش واقعی برای فروشگاه |
| نرخ تمدید و churn           | پایداری درآمد           |
| MRR و ARPU                  | پیش‌بینی درآمد          |
| تعداد تعارض همگام‌سازی      | کیفیت تجربهٔ چنددستگاهی |

> ردیابی این‌ها با همان `audit_logs` و یک جدول `events` سبک ممکن است؛ نیازی به
> سرویس خارجی نیست.

## بخش ج — ترتیب پیشنهادی اجرا

### فاز ۱ — «قابل اعتماد» (۱–۲ هفته)

1. CI کامل روی `main` (test/lint/build) + PHPStan/Pint.
2. چند کاربر و نقش‌ها (بند الف-۲).
3. صفحهٔ مرور تعارض‌های همگام‌سازی.
4. پشتیبان‌گیری خودکار شبانه + مستند بازیابی.

### فاز ۲ — «قابل فروش» (۲–۴ هفته)

5. آفلاین نسخهٔ سروری (PWA + Outbox).
6. ثبت‌نام self-service + درگاه پرداخت + تمدید/انقضا.
7. صفحهٔ قیمت‌ها و اپلیکیشن دمو.
8. ۲FA برای مدیر + سیاست رمز.

### فاز ۳ — «بازار بزرگ‌تر» (۱–۲ ماه)

9. انبار چندگانه و شمارش دوره‌ای.
10. فاکتور رسمی + QR + پیامک.
11. سند حسابداری سبک و گزارش‌های مالیاتی.
12. مدل سازمانی (چند فروشگاه زیر یک حساب) و API برای شرکای نرم‌افزاری.

هر بند از فاز ۱ امروز قابل شروع است و به تغییرات مخرب در داده نیاز ندارد.
